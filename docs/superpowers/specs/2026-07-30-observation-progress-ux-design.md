# 有效观察进度与停止提醒设计

## 目标

让第一次使用插件的普通老师在监控过程中直接知道：

- 当前有效观察时间距离题目要求还差多少；
- 页面离开时间为什么不计入有效观察；
- 现在停止是否会得到“数据不足”；
- `ready`、正常结论和数据不足分别意味着什么。

本次只改善监控侧栏及其直接依赖的数据流，不改变知识点、测试建议、
30 秒默认门槛、AI 判断规则或历史会话。

## 已确认的问题

最新失败会话持续约 190 秒，但其中 158.082 秒为 `page_away`，
最终有效观察只有 17.798 秒，低于方案要求的 30 秒。现有侧栏只显示
“17 个事件”，没有显示有效时间，导致老师把会话总时长和事件数误认为
已经满足分析条件。

另一个一致性问题是：当前停止流程只关闭正在输入的区间，不会结算最后一段
前台停顿。如果界面自行把这段等待计入进度，而停止时没有产生对应 `idle`
区间，界面会显示“已达标”，后端仍可能判定不足。

## 方案比较

### 方案 A：有效时间不足时禁用停止按钮

优点是不会产生数据不足会话。缺点是老师在隐私、误操作或采集异常时无法立即
停止，不符合“教师始终拥有停止权”的原则，因此不采用。

### 方案 B：侧栏实时进度＋不足时二次确认（推荐）

正常显示“停止监控”。有效时间不足时首次点击只展开明确提醒，不立即结束：

- `当前有效观察 17.8 / 30.0 秒`
- `页面离开 158.1 秒，不计入有效观察`
- `现在停止将得到“数据不足”`

同时提供“继续监控”和“仍要停止”两个原生按钮。达到门槛后，停止按钮直接
结束会话。该方案既降低误操作，也保留教师随时停止的权利。

### 方案 C：浏览器原生确认弹窗

实现较少，但会阻断 Jupyter 操作，信息空间有限，键盘和测试体验也弱于侧栏内
提醒，因此不采用。

## 界面设计

### 监控进行中

在“已采集事件数”上方增加一个观察进度区：

```text
有效观察时间        17.8 / 30.0 秒
[███████████░░░░░░░░]
页面离开：158.1 秒（不计入有效观察）
```

- 使用原生 `<progress>`，同时保留可读文本，不只依赖颜色。
- `aria-label` 明确为“有效观察时间进度”。
- 达标前使用项目现有中性色；达标后增加文字“已达到最低要求”。
- 当前方案没有有效时长门槛时，不显示进度条，避免伪造要求。
- 时间保留一位小数；超过门槛时文字显示实际值，进度条封顶。

### 有效时间不足时点击停止

首次点击不调用停止接口，而是在原位置显示 `role="alert"` 的内联提醒：

```text
当前有效观察 17.8 / 30.0 秒。现在停止将得到“数据不足”。
页面离开时间不计入有效观察。

[继续监控] [仍要停止]
```

- “继续监控”关闭提醒并继续采集。
- “仍要停止”明确执行现有停止、上传和分析流程。
- 达到门槛、切换会话、开始新会话或停止完成后自动清除提醒。
- 上传失败后的“重试上传/结束”不再重复询问。

### 分析状态中文化

侧栏不再直接显示内部枚举：

- `queued` → `已排队`
- `running` → `分析中`
- `ready` → `分析完成`
- `partial` → `分析完成（部分结果）`
- `error` → `分析失败`

“分析完成”只表示流程结束；结果区继续独立显示正常结论、数据不足或失败数量。

## 数据与模块边界

### `ObservationProgress`

新增一个纯 TypeScript 进度计算单元，输入已经形成的行为区间，输出：

```ts
interface IObservationProgress {
  validObservationDurationMs: number;
  pageAwayDurationMs: number;
  observationAnchorAt: string | null;
}
```

计算语义与 Python 特征提取器一致：

- 有效来源：`code_writing`、`code_deletion`、`code_paste`、`idle`；
- 排除来源：`page_away`、`code_execution`；
- 区间先合并，再从有效来源中减去排除区间；
- 页面离开时间单独合并计算；
- 不信任独立 `duration_ms`，使用最终 `started_at/ended_at`。

上传器在会话开始时重置进度，接收每个持久化区间时更新进度，并通过
`IUploadSnapshot` 发布上述三个字段。该进度只包含已经闭合的区间。

### 前台临时进度

侧栏每秒根据 `observationAnchorAt`、当前时间和页面是否仍处于前台，计算尚未
闭合的临时观察时间：

- 页面隐藏或窗口失焦时不增加；
- 临时间隔不足 2 秒时不增加；
- 一旦形成新持久化区间，以上传器发布的确定值替换临时值；
- 定时器仅在监控进行中存在，组件销毁或停止后立即清理。

### 停止时结算

`BehaviorTimelineBuilder` 增加显式 `closeObservation(occurredAt, context)`：

1. 关闭仍在输入的区间；
2. 按现有 2 秒阈值生成最后一段 `idle`；
3. 不生成伪造的切换或运行事件。

捕获控制器在 `finalize()` 前调用该方法，使侧栏进度、上传数据和后端特征保持
同一语义。

### 门槛来源

侧栏从当前已发布方案的所有维度读取
`analysis_config.minimum_observation.valid_observation_duration_ms`，
取其中最大值作为本会话需要满足的有效时长。不存在该字段时不设置时长门槛。
不在前端硬编码 30 秒。

## 异常与边界

- 时间戳无效的区间不增加进度，但仍按现有上传流程提交，由后端做最终校验。
- 页面离开过程中侧栏不可见；返回页面并形成 `page_away` 区间后立即刷新统计。
- 事件数为 0 或尚无首个有效区间时显示 `0.0 / N 秒`。
- 页面离开时间可以大于会话有效时间，两者不相减后显示负数。
- 老师确认“仍要停止”后不再因时长不足阻止上传。
- 恢复旧的未完成会话时只显示服务器已知状态，不伪造缺失的本地实时进度。

## 验收标准

1. 监控开始后显示有效观察进度和页面离开时间。
2. 进度计算与后端对同一组合区间的结果一致。
3. 保持 Jupyter 前台等待超过 30 秒后，进度显示达标；停止后后端不再因最后
   一段停顿未结算而判定不足。
4. 有效时间不足时首次点击停止不会调用 `capture.stop()`。
5. 点击“继续监控”返回采集；点击“仍要停止”才真正结束。
6. `ready` 在界面显示为“分析完成”，数据不足仍在结果区单独显示。
7. 键盘可以操作进度旁的所有按钮，提醒由辅助技术立即读出。
8. 现有前端测试、lint 和生产构建全部通过。

## 非目标

- 不执行教师配置的测试用例。
- 不改变有效观察类型或 30 秒默认配置。
- 不把页面离开时间算入有效观察。
- 不重新分析或删除旧会话。
- 不修改 AI Provider、API Key 或模型调用策略。

## 回滚

本项目当前没有 Git 元数据。实现保持为可独立撤销的文件级变更：

- 删除新增进度计算单元；
- 恢复 `IUploadSnapshot` 原字段；
- 恢复侧栏原停止按钮和状态映射；
- 移除停止前的最后停顿结算。

回滚不涉及数据迁移，也不会影响已保存会话格式。
