# 结构化 AI 响应截断恢复设计

日期：2026-08-04  
状态：实现完成，验证结果见 [结构化 AI 截断恢复与失败态验证记录](../../2026-08-04-structured-ai-truncation-recovery-verification.md)  
适用项目：JupyterLab 编程行为监控分析插件 0.2.0 Pilot

## 1. 背景与根因证据

手动验收出现两个表面不同的问题：

1. 教师在“确认测试并发布”阶段第一次生成 AI 测试建议失败，第二次手工点击才成功。
2. 完整会话已达到最低观察要求，但三个知识点全部显示“部分结果”，每项为 0 条证据。

本次会话的私有分析工件证明，采集链路、事件上传和最低观察门槛均已完成；失败发生在共享 AI 传输边界。两次会话分析请求都返回：

- `finish_reason=length`；
- `completion_tokens=4096`，恰好达到服务端默认输出上限；
- 正文 `content` 为空；
- 模型生成内容只存在于内部推理字段，不能作为结构化 JSON 结果使用。

当前 `chat_json()` 没有显式输出预算，也没有把长度截断与普通无效 JSON 区分。测试建议和会话分析共同复用该函数，因此测试建议表现为偶发首次失败；会话分析则把没有可用正文的响应映射为 `ai_analysis_failed`，最终生成三个无证据的部分结果占位卡。

## 2. 目标

1. 结构化 AI 请求首次使用明确的 8192 token 输出预算。
2. 只在提供方明确返回 `finish_reason=length` 时，自动以 16384 token 预算重试一次。
3. 同一恢复策略同时覆盖知识点建议、测试建议、会话分析和其他复用 `chat_json()` 的结构化调用。
4. 会话分析的私有审计工件保留首次截断响应和第二次响应，便于复核调用次数与失败原因。
5. 不向普通界面展示推理内容、凭据、提供方原始正文或内部异常。
6. 不调用真实外部 AI 完成自动化验收。
7. AI 分析失败且没有任何可用维度结论时，不渲染“部分结果 / 查看 0 条证据”占位卡，改为明确区分“行为采集已完成”和“AI 分析未完成”。
8. 普通 partial 结果中若某个维度没有证据声明，不渲染空的证据折叠控件；已有有效结论或证据的维度继续正常展示。

## 3. 非目标与禁止操作

- 不修改知识点、测试建议或行为分析的业务 Schema。
- 不修改采集、候选证据选择、覆盖门槛或教师复核规则。
- 不执行模型返回的测试输入或代码。
- 不对普通格式错误、业务字段错误、认证失败或不可重试 HTTP 错误自动重试。
- 不引入提供方专用的“关闭思考”参数，保持 OpenAI 兼容端点的可移植性。
- 不在本轮重构完整 AI 客户端、前端结果页或后台任务状态机。
- 不改变包含有效部分结论的 ordinary partial 分析展示，也不隐藏覆盖门槛形成的“数据不足 / 无法分析”结论。
- 不读取、输出、修改或删除现有 API Key。
- 不推送、不部署、不重启当前 JupyterLab 预览服务。

## 4. 方案比较

### 方案 A：明确预算、精确检测、一次升级重试（采用）

首次请求使用 8192；仅长度截断时使用 16384 再调用一次。它直接覆盖真实失败模式，同时把额外调用限制在可证明的截断场景。

### 方案 B：所有请求固定使用 16384

实现更简单，但每次请求都放大潜在输出和成本，且没有把截断原因形成稳定错误分类。

### 方案 C：保留 4096 并自动重试

本次会话已在相同预算下连续失败两次，重复相同请求不能修复根因。

## 5. 架构设计

### 5.1 共享传输策略

在 `myextension/llm_transport.py` 中集中定义：

- 首次结构化输出预算：8192；
- 截断恢复输出预算：16384；
- 截断恢复次数：1。

`chat_json()` 继续负责构造结构化聊天请求、调用注入或真实客户端、解析 JSON 和返回提供方元数据。每次请求体显式携带当前 `max_tokens`。

解析响应前先检查首个 choice 的 `finish_reason`：

- 值为 `length`：分类为 `provider_response_truncated`；
- 首次发生时，以 16384 预算重试；
- 第二次仍发生时，抛出不包含原始正文的 `LlmTransportError("provider_response_truncated")`；
- 其他 finish reason 沿用现有 JSON 解析与闭合校验。

### 5.2 与后台分析重试的边界

`AnalysisWorker` 现有网络重试处理超时、连接失败、429 和 5xx；该机制保持不变。长度截断恢复属于单个逻辑 `chat_json()` 调用内部的结构化输出恢复，不与网络退避次数混用。

后台使用的 `_RecordingRetryingClient` 会分别收到 8192 和 16384 两个请求体，并把提供方实际返回的两个响应都加入当前 attempt 的私有 `raw_response.json`。这样不会丢失首次截断证据，也不会创建第二个后台 attempt。

### 5.3 测试建议链路

`assessment_assistant.py` 无需增加独立重试循环。它继续调用共享 `chat_json()`：首次截断在同一个 HTTP 请求处理期间自动恢复；第二次成功后再执行既有中文、字段闭合、知识点引用和覆盖校验。

若第二次仍截断，路由沿用当前失败关闭响应，不回显提供方正文，教师仍可手工填写或再次明确触发。

### 5.4 会话分析链路

`dimension_analyzer.py` 的候选选择、结果校验和一次业务级修复请求保持不变。传输恢复成功后，模型正文进入既有 `validate_dimension_response()`；只有真实有效的维度结果才能生成证据卡。

长度截断恢复与“模型返回了合法 JSON、但缺少某些维度”的业务修复不同：

- 截断恢复：同一逻辑请求的传输级恢复；
- 维度修复：正文可解析后，对缺失或无效维度执行的既有一次修复请求。

两者各自只有一次上限，避免无限调用。

### 5.5 前端失败态保护

`src/ui/analysisResultView.ts` 在渲染结果前区分三类状态：

1. `ai_not_configured`：沿用现有“数据采集完成，尚未进行 AI 分析”空状态。
2. `ai_analysis_failed` 且所有维度都没有可用结论：显示“行为采集已完成，AI 分析未完成，可重试分析”，并展示服务端提供的数据质量原因（例如“已达到最低观察要求”）；不渲染维度占位卡、空证据折叠控件或教师复核表单。
3. 存在至少一个可用结论的 partial，或没有分析级错误的 ordinary partial：继续展示合法维度卡；单个维度只有在 `evidence_claims.length > 0` 时才显示证据折叠控件。

“可用结论”定义为维度 `decision.status === "resolved"` 或存在非空 `ai_result`。该定义保留有效的 `not_observed` 结论，因为它按契约可以没有 evidence claim；也保留覆盖门槛形成的“数据不足 / 无法分析”结论。

## 6. 数据流

```text
调用方
  → chat_json(max_tokens=8192)
  → 提供方响应
      → finish_reason != length
          → 解析 JSON → 既有业务校验
      → finish_reason == length
          → chat_json(max_tokens=16384)，仅一次
              → 成功：解析 JSON → 既有业务校验
              → 再次截断：provider_response_truncated
```

对于后台分析，每次收到的提供方响应都进入同一 attempt 的私有审计包装；普通 API 只返回已有的闭合状态和错误码。

```text
前端收到分析结果
  → ai_not_configured
      → 显示“采集完成，尚未分析”
  → ai_analysis_failed 且无可用维度结论
      → 显示“采集完成，AI 分析未完成，可重试”与数据质量原因
      → 不显示维度占位卡、0 条证据或复核表单
  → 其他 ready/partial
      → 显示合法维度卡
      → 仅 claims.length > 0 时显示证据折叠控件
```

## 7. 错误、隐私与兼容策略

- `provider_response_truncated` 仅由明确的 `finish_reason=length` 触发，避免对任意无效正文产生付费重试。
- 错误对象只保存稳定代码，不包含 response、prompt、推理字段、路径或凭据。
- 用户可见错误文案和 API 响应结构保持不变。
- 前端不新增 API 字段，也不展示 token 数、重试次数或内部错误码。
- AI 失败空状态只使用现有 `error_code`、维度决策和 `data_quality.reason`，不会根据前端猜测分析结论。
- 现有 `temperature=0` 保持不变。
- 私有响应工件继续使用现有权限、原子写入和完整性校验。
- 旧会话、旧分析结果和已发布 Profile 无需迁移。

## 8. 测试策略

所有新测试先失败，再实施最小修复。

### 8.1 共享传输单元测试

1. 首次请求包含 `max_tokens=8192`。
2. 模拟首次 `finish_reason=length`、空正文，第二次返回合法 JSON；断言调用两次、第二次为 16384、最终解析成功。
3. 模拟连续两次长度截断；断言只有两次调用并抛出稳定截断错误。
4. 模拟普通 malformed JSON；断言不触发第二次调用。
5. 模拟提供方直接返回合法映射；保持现有兼容行为。

### 8.2 测试建议回归

通过合成客户端模拟首次截断、第二次返回完整测试建议，验证 `generate_assessment_tests()` 一次调用即可成功，且中文、知识点引用、提交形式与覆盖规则仍生效。

### 8.3 后台分析回归

通过合成提供方模拟首次截断、第二次返回当前测试 Profile 的完整多维度结果，验证：

- job 进入 `ready`；
- 维度结果包含真实证据引用，不再是 0 条证据占位；
- 当前 attempt 私有原始响应包装包含两条响应；
- 不创建教师手工 retry attempt；
- 网络重试和业务维度修复的既有预算不变。

### 8.4 前端失败态回归

1. 构造 `status=partial`、`error_code=ai_analysis_failed`、所有维度均为 partial 且 `ai_result=null` 的结果；断言显示“行为采集已完成”“AI 分析未完成，可重试分析”和“已达到最低观察要求”。
2. 同一失败态不包含“部分结果”“查看 0 条证据”、维度结果卡或教师复核表单。
3. ordinary partial 仍保留维度卡和教师复核，但没有 claim 的维度不生成空证据折叠控件。
4. 有效 `not_observed` 或部分有效 AI 结论不被失败空状态错误隐藏。

### 8.5 全量验证

- 后端定向测试；
- 后端全量 pytest；
- 前端 lint 与全量 Jest，确认 API/界面没有回归；
- TypeScript 生产构建；
- 离线 wheel 构建、内容校验与源码一致性检查。

不使用真实 Key，不发送真实学生代码，不调用付费模型。

## 9. 验收标准

1. 合成首次截断场景无需用户再次点击即可生成测试建议。
2. 合成首次截断场景可让当前测试 Profile 的完整多维度会话分析进入 `ready` 并产生可核查证据。
3. 只有 `finish_reason=length` 能触发一次 16384 重试；不存在第三次调用。
4. 连续截断、普通无效 JSON和不可重试错误都失败关闭，不泄露原始内容。
5. AI 分析失败且没有可用结论时，界面明确显示采集完成与分析未完成，不显示“查看 0 条证据”、占位结果卡或复核表单。
6. ordinary partial、有效 `not_observed`、数据不足和无法分析等合法结果保持可见；无 claim 的单个维度不显示空证据控件。
7. 现有测试、lint、构建和 wheel 校验无新增失败。
8. 交付文档列出实际命令、结果、产物路径和未执行的真实 AI/部署验证。
