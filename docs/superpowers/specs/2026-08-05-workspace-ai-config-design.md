# 当前工作区 AI 配置设计

## 1. 目标

解决 BLUEDOT 工作台中插件页面可填写 AI 配置、但服务端无法将配置保存到当前容器默认位置的问题。当平台提供 `/workspace/code` 工作区时，插件应能自动将 AI 配置保存在该工作区的私有子目录中，不要求用户为此修改基础镜像。

## 2. 范围

本轮只修改：

- AI 配置文件的路径解析；
- 路径优先级、私有权限和旧行为兼容测试；
- README、BLUEDOT 接入说明和交接文档。

本轮不修改：

- 操作日志、过程日志和 AI 分析日志的存储位置；
- Jupyter Server 插件加载方式；
- BLUEDOT 基础镜像、在线工作台或密钥管理系统；
- 真实 AI 调用。

## 3. 可选方案

### 方案 A：条件化工作区回退（采用）

在保留旧配置行为的基础上，当 `/workspace/code` 存在时自动使用其下的 `.behavior-audit/.ark_ai_config.json`。优点是无需平台额外注入环境变量，且不影响普通本地用户。

### 方案 B：只增加显式环境变量

新增 AI 配置路径环境变量，完全由平台设置。边界最清晰，但用户当前无法在 BLUEDOT 页面中配置工作台环境变量，不能解决当前问题。

### 方案 C：把 API Key 编译进插件

操作最少，但 Key 会进入 wheel、镜像或共享文件，无法安全更换或撤销，不采用。

## 4. 路径解析契约

AI 配置文件按以下优先级定位：

1. `JUPYTERLAB_BEHAVIOR_AUDIT_AI_CONFIG_PATH` 指定的文件；
2. 已有 `JUPYTERLAB_BEHAVIOR_AUDIT_LOG_DIR` 存在时，使用 `<log_dir>/.ark_ai_config.json`；
3. `/workspace/code` 存在且是目录时，使用 `/workspace/code/.behavior-audit/.ark_ai_config.json`；
4. 其他环境继续使用 `~/.jupyterlab-behavior-audit/logs/.ark_ai_config.json`。

新环境变量允许正式部署覆盖默认位置；现有日志目录环境变量优先于平台探测，保持已有部署和测试兼容。

## 5. 数据与安全

- 配置内容仍只包含 Base URL、模型名和 API Key；
- 配置文件仍通过临时文件加原子替换写入，文件权限为 `0600`；
- 父目录以 `0700` 创建；
- 现有非普通文件和符号链接目标拒绝逻辑保持不变；
- 任何文档、测试和交付产物都不包含真实 Key。

`/workspace/code` 可能是平台项目的共享目录，因此本方案用于当前单用户试点工作台。多用户生产环境仍应使用平台密钥管理和显式路径。

## 6. 错误处理与兼容性

- 显式 AI 配置路径为空时视为未配置，继续下一级解析；
- `/workspace/code` 不存在或不是目录时不使用工作区回退；
- 保存失败仍由现有路由返回安全的 500 错误，不向前端泄露 Key 或绝对路径；
- 显式环境变量和普通本地默认行为保持向后兼容。

## 7. 验收标准

1. 无任何相关环境变量且模拟 `/workspace/code` 存在时，配置保存到工作区私有子目录。
2. 显式 AI 配置路径最高优先。
3. 现有日志目录环境变量仍决定旧配置文件位置。
4. 普通本地环境默认位置不变。
5. 保存后文件权限为 `0600`，状态接口不返回完整 Key。
6. 新增测试、AI 配置相关测试和项目全量质量命令通过。
7. 文档明确：当前工作区配置不等于把 Key 编译进插件，容器重置后是否保留取决于平台对 `/workspace/code` 的持久化策略。

## 8. 停止点

代码、测试和文档验证完成后停止。不自动构建或推送 BLUEDOT 镜像，不操作在线工作台，不输入真实 API Key，不调用付费 AI。
