# AI 分析延迟、可靠性与 BLUEDOT 交付设计

日期：2026-08-06

## 1. 目标与依据

修复 `myextension 0.2.1` 在会话结束后的 AI 代码分析耗时较长、偶发失败且错误原因不明确的问题，
并生成包含修复和最新 BLUEDOT AI 配置路径逻辑的离线镜像交付包。

现有真实分析记录表明：不调用外部 AI 的本地处理通常小于 `0.03` 秒；真实 Provider 成功调用约为
`15–56` 秒。历史失败多次精确发生在旧版 `10` 秒超时点，而同一任务后来以 `56` 秒成功，证明
Provider 生成时间和过短超时是主要失败来源。本地特征提取不是主要瓶颈。

当前代码允许每个逻辑请求最多三次 Provider 调用，并可能叠加长度截断恢复和无效维度修复；后台只有
一个分析线程，前端五分钟后停止自动轮询。这个组合会放大异常网络等待，并把多种 Provider 错误统一
折叠为 `ai_analysis_failed`。

## 2. 范围、禁止项与停止点

允许修改：

- AI Provider 调用预算、重试控制和安全错误映射；
- 模型输出简洁性提示，不减少证据候选范围；
- 分析状态前端中文提示；
- 后端和前端测试、项目文档；
- `deploy/bluedot/release-0.2.1/` 离线镜像交付目录；
- 从当前最新源码生成的独立 `0.2.1` wheel。

禁止操作：

- 不调用真实或付费 AI；
- 不登录、推送、登记或部署 BLUEDOT 镜像；
- 不停止或修改现有 JupyterLab 预览；
- 不覆盖或删除 `dist/` 中已有的同名 wheel；
- 不降低现有证据覆盖门槛，不删除有效候选事件，不放宽模型结果安全校验；
- 不把 API Key、token、Cookie、原始 Provider 正文或真实学生数据写入交付文件。

停止点：代码、测试、新 wheel、镜像交付文件、完整安装步骤和本地无付费验证完成后停止。真实基础
镜像构建、镜像推送、工作台验收和真实 AI 性能验收由获得授权的 BLUEDOT 管理员执行。

## 3. 已选方案与取舍

采用默认 `120` 秒的共享分析预算，兼顾现有最长 `56` 秒成功样本和一次短暂网络失败恢复。运维可将
预算配置为 `60–180` 秒；默认不使用 `180` 秒，避免让异常任务长期占用单线程队列。

不采用 `60` 秒无重试极速方案，因为已有成功调用接近 `56` 秒，网络抖动会重新产生误失败。不采用
无限或多层独立重试方案，因为其最坏等待时间超过前端轮询窗口并阻塞后续任务。

保留最多 `20` 个候选事件和每段最多 `300` 个代码字符，避免为了速度牺牲证据准确性。通过约束输出
长度降低正常生成时间，而不是删减输入证据。

## 4. 调用预算与重试

新增运行时环境变量：

```text
JUPYTERLAB_BEHAVIOR_AUDIT_ANALYSIS_TIMEOUT_SEC=120
```

规则：

- 默认值为 `120`，只接受 `60–180` 的十进制整数；缺失或非法值安全回退到 `120`；
- 单次 Provider 调用上限为 `60` 秒，并且不得超过当前任务剩余预算；
- 初始分析、显式长度截断恢复、无效维度修复和瞬时网络重试共享同一个预算；
- 只对网络错误、超时、HTTP `429` 和 `5xx` 自动重试一次，退避 `2` 秒；
- HTTP `400/401/403`、非 JSON、Schema 不合法等确定性错误不做网络重试；
- 只有 Provider 明确返回 `finish_reason=length` 时才保留现有 `8192 -> 16384` 一次恢复；
- 只有首次响应已经返回且存在缺失或无效维度时才进行一次格式修复；
- 开始任何恢复或修复前先检查剩余预算；预算不足时返回稳定错误，不启动注定超时的新请求。

Python `urllib` 的 timeout 是网络操作超时而非可强制终止线程的精确墙钟定时器。因此 `120` 秒是
调度层的共享预算；单次网络调用仍由 `60` 秒 socket timeout 提供上界，极端底层网络行为可能产生
小幅超出，但不会再获得新的完整重试预算。

## 5. 输出压缩与准确性

模型继续一次接收所有满足覆盖度要求的教师维度和最多 `20` 个候选事件。系统提示和输出 Schema
描述增加以下明确要求：

- 每个维度只返回最多 `3` 条最强、互不重复的证据；
- 每条 claim 使用简洁中文；
- explanation 不超过 `160` 个中文字符；
- 不输出分析过程、Markdown 或 Schema 之外的字段。

服务端继续兼容现有最多 `500` 字 explanation 和既有证据数组，不收紧持久化 API Schema，避免破坏
历史结果和客户端兼容。输出约束用于减少模型生成量，不改变教师复核能力。

## 6. 稳定错误码

Provider 与模型输出失败映射为以下公开、安全、无正文错误码：

| 错误码 | 条件 | 前端提示重点 |
| --- | --- | --- |
| `ai_analysis_timeout` | 共享预算耗尽或 Provider 超时后仍未恢复 | 分析超时，可重试或检查模型速度 |
| `ai_provider_network_error` | 网络错误重试后仍失败 | 检查出站网络、DNS 和 TLS |
| `ai_provider_rate_limited` | HTTP 429 重试后仍失败 | 稍后重试并检查额度/并发 |
| `ai_provider_auth_failed` | HTTP 401/403 | 检查 API Key 和模型权限 |
| `ai_provider_request_rejected` | 其他不可重试 4xx | 检查 Base URL、模型名和请求兼容性 |
| `ai_provider_unavailable` | 5xx 重试后仍失败 | Provider 暂不可用，稍后重试 |
| `ai_response_truncated` | 两次显式长度预算均截断 | 输出过长，调整题目维度或模型 |
| `ai_response_invalid` | 非 JSON 或修复后仍不满足维度契约 | 模型输出格式不符合要求 |
| `ai_analysis_failed` | 未分类的安全兜底 | 分析未完成，可重试 |

错误码进入现有 job/attempt 状态和前端 `actionForError()`。不得持久化异常文本、响应正文、请求体、
绝对路径或凭据。已有 `ai_not_configured` 和 `invalid_profile` 语义保持不变。

## 7. 后台与前端行为

后台仍使用一个有界线程和现有持久化 job/attempt 状态机，保持当前单用户 Pilot 的顺序与恢复语义。
一个任务的所有外部调用共享预算，达到终态后立即释放队列。

前端继续按 `1、2、4、8、10...` 秒退避轮询，最长五分钟。默认预算短于轮询窗口，因此正常情况下
前端能看到明确终态。失败时显示具体中文操作建议，并保留现有“重试分析”按钮。错误提示不得暗示
行为采集失败；已保存的操作日志和过程日志继续可查看、可下载。

## 8. 测试策略

实现必须遵循 TDD，先增加失败测试，再写最小实现。

后端测试至少覆盖：

- 环境变量缺失、边界值、非法值和默认值；
- 所有逻辑请求共享同一单调时钟预算；
- 瞬时错误最多一次重试且只等待 `2` 秒；
- 确定性 4xx 和无效响应不做网络重试；
- 长度恢复和维度修复不能绕过共享预算；
- 每次传给 Provider 的 timeout 不大于 `60` 秒且不大于剩余预算；
- 具体 LLM transport 错误映射为稳定 job 错误码；
- 原始异常文本和 Provider 正文不进入公开结果；
- 输出提示包含最多三条证据和 160 字说明约束；
- 既有覆盖度、候选选择、有效结果、教师复核和重启恢复回归不变。

前端测试覆盖每个新错误码的中文操作建议、失败状态和重试按钮。

质量门禁：后端全量 pytest、前端 Jest、lint、生产前端构建、wheel 内容检查、ZIP 完整性、SHA-256
和隔离安装导入全部通过。合成 Provider 测试不 sleep、不联网、不调用真实 AI。

真实延迟和成功率只能在授权的目标网络和模型上验收；本地合成测试证明预算与重试逻辑正确，不能
代替真实 Provider 性能结论。

## 9. BLUEDOT 交付

沿用已批准的独立目录：

```text
deploy/bluedot/release-0.2.1/
├── README.md
├── Dockerfile
├── .dockerignore
├── artifacts/
│   └── myextension-0.2.1-py3-none-any.whl
├── SHA256SUMS
├── build_image.sh
├── verify_image.sh
└── runtime.env.example
```

新 wheel 从包含本次修复和 2026-08-05 BLUEDOT 配置路径逻辑的当前源码构建。现有
`dist/myextension-0.2.1-py3-none-any.whl` 保留不变；新 wheel 使用交付目录和新 SHA-256 区分。

Dockerfile 在 BLUEDOT `PyTorch-2.5.1-JupyterLab4` 基础镜像的原 Python/Jupyter 环境中使用
`--no-deps` 安装 wheel，构建时检查 JupyterLab 4、Jupyter Server 2、`jsonschema`、前端扩展和
服务端扩展。镜像不安装 Node.js，不包含 API Key，不改变基础镜像入口。

`runtime.env.example` 包含：

```text
JUPYTERLAB_BEHAVIOR_AUDIT_LOG_DIR=/workspace/result/behavior-audit
JUPYTERLAB_BEHAVIOR_AUDIT_ANALYSIS_TIMEOUT_SEC=120
ARK_BASE_URL=https://ark.cn-beijing.volces.com/api/coding/v3
ARK_MODEL=glm-5-2-260617
```

只注明 `ARK_API_KEY` 必须由平台密钥管理在运行时注入，不提供值。需要分离密钥配置和教学输出时，
使用 `JUPYTERLAB_BEHAVIOR_AUDIT_AI_CONFIG_PATH` 指向受控私有卷。

## 10. 安装、验收与回滚

交付 README 必须完整说明：准备基础镜像地址、核对 wheel SHA-256、运行构建脚本、本地验证镜像、
登录单位镜像仓库、推送、在 BLUEDOT 登记新框架版本、创建新工作台、挂载 `/workspace/result`、注入
运行配置、完成合成会话、验证三份日志、授权后执行真实 AI 性能验收，以及失败时切回上一镜像。

真实验收标准：正常样本应在 120 秒内进入 ready 或明确失败终态；前端不应在后端仍可能无限重试时
停留在未知状态。分析失败不影响已完成的行为采集和非 AI 日志。

回滚以旧镜像 digest/不可变标签为准。软件回滚不自动删除持久化教学数据，数据删除需单独授权。
