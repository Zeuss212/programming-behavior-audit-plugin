# 完整行为分析超时自动重试设计

日期：2026-08-06  
分支：`fix/ui-hotfix-0.2.1`

## 背景与现场证据

完整行为分析当前使用 120 秒总预算和 60 秒单次 Provider 调用上限。一个持久化分析
attempt 内部最多调用 Provider 两次；可重试错误之间固定等待 2 秒。

最新隔离预览中的同一分析任务产生了以下证据：

- 第一个持久化 attempt 从 `09:23:30.607` 运行到 `09:25:30.740`，约
  120.13 秒，状态为 `partial`，错误码为 `ai_analysis_timeout`；Provider 响应快照
  中响应数为 0；
- 教师手动重试后，第二个持久化 attempt 从 `09:25:40.935` 运行到
  `09:26:38.752`，约 57.82 秒，状态为 `ready`，六个维度均生成了 AI 结果；
- 两次 attempt 使用同一任务输入。因此题目、方案、AI 配置和结果结构不是本次失败的
  根因。可观测根因是 Provider 延迟波动超过了当前 120 秒恢复窗口；首次冷启动或服务
  排队是合理推断，但现有安全日志不能进一步区分 Provider 内部原因。

## 目标与非目标

目标：

1. 完整分析遇到可重试的 Provider 故障时，在单个可审计 attempt 内最多执行三次调用；
2. 默认总预算改为 180 秒，单次调用仍不超过 60 秒；
3. 真实 60 秒超时后立即重试，避免固定退避挤占下一次调用预算；
4. 429、5xx 和快速网络错误仍采用 2 秒退避；
5. 页面在任务运行期间明确提示系统会自动重试及最长等待时间，不提前显示最终失败；
6. 保留现有手动重试、attempt 审计和安全错误码。

非目标：

- 不修改题目、知识点和测试建议生成的快速请求配置；
- 不修改 Provider、模型、提示词、输出预算或深度思考配置；
- 不新增持久化 job/attempt 状态，不改变公开 API 契约；
- 不进行真实 BLUEDOT 部署、镜像构建、推送或真实课程数据测试。

## 方案比较

### 方案 A：单 attempt 内三次 60 秒调用（采用）

将默认完整分析总预算设为 180 秒，并由总预算与单次调用上限计算最大调用次数；默认
得到三次。Provider 明确超时说明已经自然等待过 60 秒，因此不再额外退避。其他通常
会快速返回的可重试错误继续等待 2 秒。

优点是改动集中在现有传输重试边界，不改变 job 状态机、磁盘结构或 API；页面现有
`running` 状态能够覆盖整个自动恢复过程。缺点是一次持续异常最多占用工作线程约
180 秒，并可能产生三次 Provider 请求。

### 方案 B：失败后自动创建第二个持久化 attempt（不采用）

优点是每次自动重试都单独留痕。缺点是需要扩展 job 状态机、重试原因、并发/删除竞态
和前端投影，还要防止自动重试与教师手动重试重复，超出本轮可靠性修复的必要范围。

### 方案 C：两次 90 秒调用（不采用）

该方案减少调用次数，但单次故障恢复更慢，并改变已有 60 秒 Provider 超时边界。现场
第三次调用在 57.82 秒成功，优先增加一次 60 秒恢复机会更符合证据。

## 后端设计

### 配置与预算

- `DEFAULT_ANALYSIS_TIMEOUT_SEC` 从 120 改为 180；
- 环境变量 `JUPYTERLAB_BEHAVIOR_AUDIT_ANALYSIS_TIMEOUT_SEC` 继续接受 60 到
  180 秒的闭合整数；
- `PROVIDER_CALL_TIMEOUT_SEC` 保持 60 秒；
- 最大调用次数由 `ceil(total_timeout_sec / PROVIDER_CALL_TIMEOUT_SEC)` 得到，并
  受总 deadline 约束，因此 60/120/180 秒预算分别最多调用 1/2/3 次；
- 每次实际传给 Provider 的 timeout 仍是 `min(60, ceil(remaining))`。

### 重试分类

维持现有可重试集合：

- `provider_timeout`；
- `provider_network_error`；
- HTTP 429；
- HTTP 5xx。

认证失败、其他 4xx、响应格式无效、结构校验失败和输入完整性错误不自动重试。

退避策略：

- `provider_timeout`：立即进入下一次调用；前一调用本身已经消耗了等待时间；
- 其他可重试错误：保持 2 秒退避，但只有 deadline 仍有可用时间时才继续；
- deadline 耗尽时继续映射为现有 `ai_analysis_timeout`，不新增外部错误码。

### 审计与数据

三次 Provider 调用属于同一个持久化 attempt。只有成功解码的原始响应进入现有响应
快照；超时不写入响应正文。若全部失败，attempt 仍以 `partial` 和
`ai_analysis_timeout` 结束，教师仍可手动创建下一 attempt。现有输入哈希、响应哈希、
prompt 快照和删除并发保护保持不变。

## 前端设计

不增加轮询接口字段。任务状态为 `queued` 或 `running` 时，在现有分析状态区域显示：

> AI 正在分析；响应较慢时会自动重试，最长约 180 秒。

终态仍使用现有错误翻译和“重试分析”按钮。这样不会把一次内部 Provider 超时误报成
最终失败，也不需要前端猜测当前是第几次内部调用。

## 异常和边界条件

- 自定义总预算为 60 秒时只调用一次；120 秒时最多两次；180 秒时最多三次；
- Provider 在 deadline 临界点返回时，以已有 deadline/调用返回语义为准，不在响应
  已成功返回后人为判失败；
- 快速连续 429/5xx 会执行短退避，但 deadline 永远是硬上限；
- 工作线程重启仍走现有 `interrupted_after_restart` 恢复逻辑；
- 教师删除会话、重复点击手动重试和队列满仍由现有并发保护处理。

## 测试与验收

后端单元测试使用假时钟和假 Provider，不访问真实网络：

1. 默认预算为 180 秒；非法或越界配置仍回退默认值；
2. 两次超时后第三次在剩余预算内成功，只产生一个持久化 attempt；
3. 超时重试之间不调用 wait；
4. 网络错误、429、5xx 仍调用 2 秒 wait；
5. 非可重试错误只调用一次；
6. 60/120/180 秒配置分别限制为最多 1/2/3 次；
7. 三次均超时后仍产生 `partial`/`ai_analysis_timeout`，手动重试仍可用。

前端 Jest 覆盖 queued/running 提示和终态重试按钮。随后执行完整 pytest、Jest、覆盖率、
Stylelint、Prettier、ESLint、TypeScript 生产构建、JupyterLab 预构建、wheel 结构与
隔离安装验证。
