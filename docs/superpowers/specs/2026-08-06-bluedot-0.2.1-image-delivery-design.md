# BLUEDOT 0.2.1 镜像离线交付设计

日期：2026-08-06

## 1. 背景与现场证据

项目是 JupyterLab 4 预构建前端扩展与 Jupyter Server 扩展，Python 包名为
`myextension`，插件 ID 为 `myextension:plugin`，当前版本保持 `0.2.1`。

当前目录不是 Git 仓库，无法使用分支或 commit 标识“最新代码”。最新性以源码修改时间、
自动化验证结果、wheel 内容和 SHA-256 共同证明。

现有 `dist/myextension-0.2.1-py3-none-any.whl` 的 SHA-256 为
`7138965244a5f71b9307ca89c5585cdb58aa1206a2ba1a0c13e57147bbeecf98`，但该 wheel
早于 2026-08-05 的 `myextension/llm_transport.py` 修改。旧 wheel 不包含最新 BLUEDOT AI
配置路径逻辑，不能作为本次“最新代码”镜像制品。现有 wheel 保留不覆盖，本次在独立交付目录
生成同版本、不同 SHA-256 的新 wheel。

最新配置路径逻辑已有 4 项定向测试，实际执行结果为 `4 passed`。

## 2. 本轮目标

生成一套可移交给 BLUEDOT 平台管理员的 `myextension 0.2.1` 离线镜像交付包，使管理员
能够在 `PyTorch-2.5.1-JupyterLab4` 基础镜像上安装插件、构建自定义镜像、注入运行时配置、
验证插件、推送镜像并在失败时回滚。

交付包必须包含从当前最新源码重新生成的 wheel，并明确区分旧 wheel 和新 wheel。

## 3. 范围与停止点

### 3.1 允许操作

- 读取当前项目源码、测试、构建配置和既有 BLUEDOT 文档；
- 执行本地测试、lint、生产前端构建、wheel 构建与内容校验；
- 在 `deploy/bluedot/release-0.2.1/` 创建交付文件；
- 使用本机已安装工具执行无网络、无付费的验证；
- 如本机存在可用 Docker，可做不接触真实 BLUEDOT 的静态或本地构建验证；若缺少真实基础镜像，
  如实记录未验证项。

### 3.2 禁止操作

- 不覆盖或删除现有 `dist/` wheel；
- 不修改、停止或接管现有 JupyterLab 预览；
- 不登录 BLUEDOT，不推送镜像，不登记平台框架版本，不部署真实工作台；
- 不调用真实或付费 AI；
- 不把 API Key、Jupyter token、Cookie 或真实学生数据写入文件、镜像层、命令示例或日志；
- 不把当前 Pilot 描述为已经具备正式多租户隔离能力。

### 3.3 停止点

完成本地交付包、自动验证和完整中文说明后停止。镜像推送、平台登记、真实工作台验收和真实 AI
验收由取得授权的 BLUEDOT 管理员执行。

## 4. 已选方案

采用独立离线镜像交付包。先在项目环境中从最新源码构建 prebuilt wheel，再将固定 wheel 安装到
BLUEDOT 基础镜像。普通镜像构建过程不安装 Node.js，也不在镜像内重新编译前端。

不采用以下方案：

- 直接替换 `dist/` 中的同名 wheel：容易覆盖既有交付证据；
- 在 Docker 多阶段构建中从源码编译：会引入 Node/Yarn/Python 构建依赖和网络不确定性；
- 通过 PyPI Manager 临时安装：工作台重建后可能丢失，不能作为正式镜像交付方式。

## 5. 交付目录

```text
deploy/bluedot/release-0.2.1/
├── README.md
├── Dockerfile
├── .dockerignore
├── artifacts/
│   └── myextension-0.2.1-py3-none-any.whl
├── SHA256SUMS
├── build_image.sh
├── verify_image.sh
└── runtime.env.example
```

文件职责：

- `README.md`：前置条件、构建、推送、运行时配置、平台登记、验收、排障和回滚的完整中文步骤；
- `Dockerfile`：接收基础镜像地址，在其原有 Python/Jupyter 环境安装固定 wheel，并执行构建期检查；
- `.dockerignore`：只允许镜像构建所需文件进入上下文，排除配置、日志和无关源码；
- `artifacts/*.whl`：从当前最新源码生成的唯一安装制品；
- `SHA256SUMS`：记录新 wheel 的交付哈希；
- `build_image.sh`：要求调用方显式提供基础镜像和目标镜像标签，核对 wheel 哈希后调用 Docker 构建；
- `verify_image.sh`：以指定镜像运行非交互验收，检查包版本、前端扩展、服务端扩展和日志路径；
- `runtime.env.example`：只列非敏感配置和密钥变量名，不包含密钥值。

## 6. 最新 0.2.1 配置逻辑

AI 配置文件按以下顺序选择，前项存在时不再使用后项：

1. `JUPYTERLAB_BEHAVIOR_AUDIT_AI_CONFIG_PATH` 指向的明确文件；
2. 设置 `JUPYTERLAB_BEHAVIOR_AUDIT_LOG_DIR` 时，使用该目录下的 `.ark_ai_config.json`；
3. 未设置以上路径且 `/workspace/code` 存在时，使用
   `/workspace/code/.behavior-audit/.ark_ai_config.json`；
4. 其他环境使用普通本地日志根目录下的 `.ark_ai_config.json`。

保存逻辑创建私有父目录，并将配置文件写为 `0600`。环境变量中已有值优先于配置文件值。
镜像默认设置：

```text
JUPYTERLAB_BEHAVIOR_AUDIT_LOG_DIR=/workspace/result/behavior-audit
```

因此镜像默认会把配置文件放到持久化日志根目录。若平台需要将密钥配置与教学输出分离，应在运行时
额外设置 `JUPYTERLAB_BEHAVIOR_AUDIT_AI_CONFIG_PATH`，将其指向平台受控私有卷。

## 7. 构建与运行数据流

```text
最新源码
  -> 测试、lint、生产前端构建
  -> 独立目录生成 0.2.1 wheel
  -> wheel 内容与 SHA-256 校验
  -> Docker 安装到 BLUEDOT 原有 Python/Jupyter 环境
  -> 构建期扩展检查
  -> 平台运行时注入非敏感配置和密钥
  -> Jupyter Server 加载前后端扩展
  -> 教学日志写入 /workspace/result/behavior-audit
```

镜像保留基础镜像原有 `ENTRYPOINT`、`CMD`、工作目录和用户语义。插件不单独开放网络端口，API
继续使用 Jupyter Server 的认证和动态 base URL。

## 8. Dockerfile 约束

- 基础镜像通过必填构建参数传入，不在交付包中猜测内部仓库地址；
- 只复制 `artifacts/myextension-0.2.1-py3-none-any.whl`；
- 使用 `python -m pip`，保证安装到与镜像内 `python` 一致的环境；
- 使用 `--no-cache-dir --no-deps` 安装 wheel，避免构建时联网或意外升级 Jupyter 依赖；
- 安装前验证基础镜像已有兼容的 JupyterLab 4、Jupyter Server 2 和 `jsonschema`；
- 显式启用 Jupyter Server 扩展；prebuilt labextension 由 wheel 安装到 sys-prefix，并执行列表检查；
- 构建失败时立即停止，不生成“部分可用”的镜像；
- 不使用 `ARG`、`ENV` 或 `COPY` 写入任何密钥；
- 日志目录只通过 `ENV` 声明，不在构建阶段写入真实数据。

若 BLUEDOT 基础镜像默认用户无权写入 sys-prefix，平台管理员必须使用该基础镜像既有的 root
构建/非 root 运行模式。交付包不猜测未知用户名，也不回退到 `pip --user`。

## 9. 运行时配置

非敏感配置可以由平台运行时注入：

```text
JUPYTERLAB_BEHAVIOR_AUDIT_LOG_DIR=/workspace/result/behavior-audit
ARK_BASE_URL=https://ark.cn-beijing.volces.com/api/coding/v3
ARK_MODEL=glm-5-2-260617
```

以下变量只列变量名，不提供值：

```text
ARK_API_KEY
```

正式环境由 BLUEDOT 密钥管理能力在运行时注入 `ARK_API_KEY`。如需独立私有配置卷，运行时设置：

```text
JUPYTERLAB_BEHAVIOR_AUDIT_AI_CONFIG_PATH=/平台受控私有目录/.ark_ai_config.json
```

`/workspace/result` 必须由平台持久化，并保证 Jupyter 运行用户可读写。该目录可能包含学生代码、输出、
错误文本和分析结果，必须继承单位的数据访问、保留、导出和删除政策。

## 10. 错误处理

- wheel 缺失或 SHA-256 不匹配：构建脚本在调用 Docker 前失败；
- 基础镜像参数或目标标签缺失：构建脚本显示用法并返回非零；
- 基础镜像不是 JupyterLab 4 / Server 2：Docker 构建失败；
- 依赖缺失：`--no-deps` 安装前检查失败，并明确由基础镜像维护者补齐；
- sys-prefix 无写权限：安装失败，不回退到用户目录；
- 前端或服务端扩展未启用：构建期或镜像验收失败；
- `/workspace/result` 不可写：运行验收失败；
- AI 未配置：插件仍可采集并生成非 AI 日志，不把该状态伪装成 AI 分析成功；
- 平台镜像验证失败：不推送、不登记，继续使用上一已验证镜像。

## 11. 验证策略

### 11.1 源码与 wheel

- 定向运行最新 BLUEDOT 配置路径测试；
- 运行后端全量测试、前端 Jest、lint 和生产构建；
- 构建 wheel 到独立临时目录，再复制到交付目录；
- 运行 wheel ZIP 完整性检查和项目已有的 wheel 内容检查；
- 从 wheel 中读取 `myextension/llm_transport.py`，确认包含配置路径环境变量和
  `/workspace/code/.behavior-audit` 回退逻辑；
- 在隔离安装目录导入 `myextension` 并确认版本为 `0.2.1`；
- 生成并复核 `SHA256SUMS`。

### 11.2 镜像

构建期和 `verify_image.sh` 至少检查：

```text
python -c "import myextension; print(myextension.__version__)"
jupyter labextension list
jupyter server extension list
日志根目录可创建且可写
```

若没有 BLUEDOT 真实基础镜像或本机 Docker 不可用，文件和 wheel 验证仍须完成，并明确将镜像构建、
镜像运行与平台验收列为管理员待执行项，不得宣称镜像已实机通过。

### 11.3 平台验收

管理员使用新镜像创建全新工作台，验证：

1. 动态 `/notebook_<uuid>/` 前缀下侧栏与 API 正常；
2. 创建并发布合成题目方案；
3. 开始监控，产生编辑、一次执行失败、修复和执行成功；
4. 停止后 `operation_log.json` 和 `process_log.md` 可查看、可下载；
5. 未授权真实 AI 时不调用外部模型；授权后才验收 `analysis_log.json`；
6. 重建工作台后检查 `/workspace/result/behavior-audit` 的持久化结果；
7. 确认镜像和输出中不存在 API Key、Jupyter token 或 Cookie。

## 12. 回滚

保留上一已验证镜像的不可变标签或 digest。新镜像失败时，将 BLUEDOT 工作台模板指回上一镜像，
创建新工作台复验。软件回滚不会删除 `/workspace/result/behavior-audit`；教学数据的保留或删除必须
单独授权。

由于本次保持版本号 `0.2.1`，平台侧必须使用新的镜像标签或 digest 和新 wheel SHA-256 区分制品，
不得只根据 Python 版本号判断镜像内容。

## 13. 验收标准

- 交付目录中的文件完整且脚本通过语法检查；
- 新 wheel 从当前最新源码生成，不覆盖旧 wheel；
- 新 wheel 版本为 `0.2.1`，包含最新 BLUEDOT 配置路径逻辑；
- wheel 完整性、内容、隔离导入和适用的项目质量命令通过；
- `SHA256SUMS` 与实际新 wheel 一致；
- Dockerfile 不包含密钥、不要求 Node.js、不在镜像内从源码编译；
- README 给出从取得基础镜像地址到构建、验证、推送、平台配置、验收和回滚的完整步骤；
- 未实际完成的 Docker 或 BLUEDOT 验证以明确待办交接，不做虚假完成声明。
