# C++ 课堂可信测评闭环设计

设计日期：2026-08-27

关联前端设计：`2026-08-27-teacher-assessment-dimension-step-design.md`

## 目标

把教师配置、学生编程、受控测试、证据上传、掌握判定、课堂列表和学生简报连成一条可追溯闭环。最终页面中的每一个掌握结论、问题描述和教学建议都必须能回到已发布的教师标准与真实课堂事件，不能由 AI 猜测或补写。

本期以两类 C++ 代码补全练习为首批真实场景：顺序表基本操作与链表逆置。教师已经提供题目说明、测试用例和可供学生完成的 C++ 源框架；学生在自己的实验环境中补全代码并运行课堂测试。

## 角色与核心问题

### 教师

- 配置时要知道“最终按什么判断”，并能在发布前确认知识点、测评维度、测试覆盖和源框架。
- 上课时即使不打开单个简报，也能从学生列表看出谁已掌握、谁部分掌握、谁有明确未达项、谁只是证据不足。
- 打开简报后能立即看到未达到的具体要求、对应测试或过程证据，以及下一步教学动作。

### 学生

- 清楚要完成哪个源框架、如何运行课堂测试、哪些要求已经达到、哪些仍需修改。
- 不因尚未运行、上传中断或数据缺失而被误判为“未掌握”。
- 能看到基于自己真实测试结果生成的下一步建议，而不是泛化评价。

## 已确认的判定口径

对每个知识点应用以下互斥状态：

1. `mastered`（已掌握）：该知识点的全部教师定义测评要求都有有效支持证据，并且至少存在一次与该知识点相关、在当前已发布方案和当前源代码上通过的受控测试运行。
2. `partial`（部分掌握）：至少一个要求有支持证据，但仍有其他要求缺少证据；简报必须逐项列出已满足与缺少内容。若存在明确违反项，不得使用 `partial` 掩盖。
3. `evidence_insufficient`（证据不足）：没有足够的已上传、可校验证据，或证据链不完整。此状态永远不能自动转换为“未掌握”。
4. `not_mastered`（明确未掌握）：只有真实受控测试或其他可验证事件明确违反教师发布前定义的要求时才使用，并必须附上对应测试 ID 或事件引用。
5. `review_required`（待教师复核）：证据相互冲突、方案关联不一致、完整性校验失败，或系统无法安全应用上述规则。

教师复核可以覆盖自动结论，但必须保存原自动结论、覆盖后的状态、理由、教师身份和时间，形成追加式审计记录。

## 当前基线与缺口

现有系统已经具备可复用的基础：

- 课堂方案草稿、不可变发布版本、学生分配与课堂会话；
- 行为事件分块上传、连续序号和内容哈希；
- 学生简报、可选 AI 证据分析、教师复核和异步任务；
- 教师课堂列表与单个学生简报页面；
- 持久化异步课堂方案建议任务。

但当前实现不能直接满足本设计：

- 方案建议只按请求内容去重，完成后同一课堂仍可再次生成；
- `profile-draft-v2` 固定为 Python，自动要求也主要是 Python 字典语法；
- 已配置的测试用例只进入发布资料，没有在学生环境中作为受控测试执行；
- 普通 `code_execution=success` 只能证明进程成功，不能证明答案正确；
- v1 简报没有可信的 `not_mastered` 状态与逐要求证据结果；
- 课堂契约没有源框架的不可变引用。

因此页面可以实现，但必须先补齐下面的服务端、插件和契约能力，不能用前端本地状态或模拟数据冒充闭环。

## 总体架构

数据流固定为：

教师编写会话 → 一次性 AI 方案建议 → 教师修改并确认 → 发布不可变 C++ 方案 → 学生领取源框架 → 学生运行受控测试 → 结构化测试事件与过程事件上传 → 确定性掌握引擎 → 可选 AI 证据解释 → 教师列表／学生简报 → 教师复核

职责边界：

- FinColab 教师前端负责配置、确认、恢复页面状态和展示结果，不在浏览器内计算掌握结论。
- `classroom-sync` 负责所有权、方案版本、一次生成约束、证据完整性、简报持久化与读模型。
- 学生实验环境内的受信插件负责调用固定 C++ 工具链、执行教师测试并生成结构化测试事件。
- AI 只生成可编辑的方案草稿，或对已有事件做带引用的解释；AI 不能执行代码、生成最终测试结果或覆盖确定性掌握结论。

## 1. 一次性 AI 课堂方案建议

### 生成范围

“一次生成”以一次教师编写会话为边界，而不是浏览器标签页或请求文本：

- 一次建议覆盖整份题目，返回课堂标题、知识点与每个知识点的测评维度草稿；
- 不提供逐知识点生成、局部重新生成或成功后的再次生成；
- 建议应用后教师可以任意手工修改，发布内容以教师最终确认版本为准；
- 页面刷新、多个标签页或换浏览器后读取同一份服务端结果。

### 编写会话

新增 `PlanAuthoringSession`：

- `id`、`teacher_id`、`space_id`、`parent_algorithm_id`；
- `status`: `open | published | abandoned`；
- `active_slot`: 打开时为 `1`，关闭后为 `null`；
- `suggestion_job_id`、`published_plan_id`、`created_at`、`updated_at`、`closed_at`。

数据库保证同一教师、同一父实验最多有一个打开的编写会话。发布或明确放弃后才能开始下一次编写会话。它是轻量编写边界，不代替正式 `PlanDraft`。

### API 行为

- `POST /v1/classroom/plan-authoring-sessions`：按教师与父实验幂等返回当前打开会话；没有时创建。
- `GET /v1/classroom/plan-authoring-sessions/current?space_id=...&parent_algorithm_id=...`：恢复当前会话及建议状态。
- `POST /v1/classroom/plan-authoring-sessions/{id}/plan-suggestion`：首次调用创建异步任务；若已有 `pending` 或 `ready` 任务则返回原任务，不接受第二份输入。
- `GET /v1/classroom/plan-authoring-sessions/{id}/plan-suggestion`：返回 `not_requested | pending | ready | failed`，`ready` 时返回持久化建议。
- `POST /v1/classroom/plan-authoring-sessions/{id}/abandon`：只有会话所有者可明确放弃尚未发布的编写会话；保留审计但释放 `active_slot`。
- 创建正式草稿时携带 `authoring_session_id`；发布成功后同一事务关闭编写会话并关联 `plan_id`。

现有 `ClassroomPlanSuggestionJob` 继续承担租约、内部重试和隐私最小化。新增 `authoring_session_id`，并以它限制唯一活跃／成功建议。提供商短暂故障可以在同一任务内自动重试；终态失败后页面转为手工编辑，不再显示重新生成按钮。

任务保存请求时的 `input_hash`。若教师在等待期间修改了题目，结果仍可查看，但页面必须标记“建议基于较早版本的题目”；应用前显示将整份替换的明确确认，不能静默覆盖新内容，也不能据此重新生成。

## 2. C++ 方案契约 v3

新增 `profile-draft-v3.json` 与 `profile-version-v3.json`，保留 v2 Python 方案原样兼容。课堂 plan-draft/plan-version 合同允许嵌套 v2 或 v3 profile；旧方案、旧学生会话和旧简报不迁写。

### 问题与工具链

`problem_context` 至少包含：

- `language: "cpp"`；
- `submission_contract.kind: "stdin_stdout"`；
- `toolchain_profile: "cpp17_stdio_v1"`；
- `entry_file`：仅允许安全文件名，不允许路径、命令或 shell 参数。

工具链配置由服务端版本化白名单定义，教师不能输入编译命令、可执行路径或任意编译参数。首版固定 C++17。

### 源框架引用

新增只读 `starter_source`：

- `artifact_id`：FinColab 父实验中已存在材料的稳定标识；
- `display_name` 与安全 `file_name`；
- `sha256`、`size_bytes`；
- `source: "fincolab_experiment"`。

前端不新增虚假的上传、下载或源框架编辑功能。它只显示从父实验材料接口读取到的真实文件及校验状态。发布时服务端重新解析并校验该引用；材料缺失、哈希变化或语言不匹配时阻止发布。

### 材料解析边界

新增服务端 `AssessmentMaterialGateway`，把 FinColab 父实验中的真实材料投影为结构化、只读的测评材料包。教师页面调用：

- `GET /v1/classroom/experiments/{space_id}/{parent_algorithm_id}/assessment-materials`；
- 返回源框架引用、已结构化教师测试、材料哈希、解析状态和稳定错误码；
- 所有权校验与现有父实验接口一致。

浏览器不解析 C++ 或自然语言 TXT，不把文件名推断成测试，也不让 AI 把说明文字直接变成可执行测试。若上游当前只能提供原始文件，必须先实现有版本的服务端导入／解析适配器，并让教师在既有材料流程中确认结构化结果；在此之前页面显示“材料尚未结构化，无法发布”。

### 测试用例

每个启用测试包含：

- `id`、`name`、`knowledge_point_ids`、`criterion_ids`、`order`；
- `kind: "stdin_stdout"`；
- `input`、`expected_stdout`；
- `comparison: "normalized_text_v1"`；
- `timeout_ms`，取服务端允许范围；
- `source: "teacher"`；
- `content_hash`。

`normalized_text_v1` 只统一换行符并忽略每行末尾空白，不做模糊语义匹配。需要数值容差等新策略时必须增加新的明确版本，不能让 AI 临时解释。

发布要求：每个知识点及其每个必需测评要求至少被一个启用测试覆盖；测试引用的知识点和 criterion 必须一致；测试哈希、知识点／测评维度哈希和源框架哈希均由教师确认且与当前草稿一致。

### 测评维度

每个知识点仍对应一个教师可读测评维度。维度保留：

- `question`：教师在页面填写的最终评判标准；
- `evidence_criteria[]`：用于记录该维度下可核验的要求，测试通过 `criterion_ids` 单向关联，避免两份映射不一致；
- `analysis_config.mode: "evidence_binding"`。

首版 UI 仍以一段测评维度文字为核心，不让 AI 在教师确认后新增要求。系统仅把教师测试的通过／失败作为已发布要求的确定性证据；过程证据只能在有事件引用时补充说明。

## 3. 学生受控 C++ 测试

### 触发方式

学生从受信插件界面执行“运行课堂测试”。普通终端或编辑器中的任意运行仍记录为过程事件，但不会单独证明知识点掌握。

插件只允许测试当前分配方案指定的 `entry_file`，并校验：

- 当前 `plan_id`、`plan_version` 和 profile `content_hash`；
- 源文件位于分配的工作区内且不是符号链接；
- 文件名、文件大小和文本编码满足白名单；
- 测试 ID、输入与预期输出来自不可变已发布方案。

### 隔离与资源限制

不在浏览器或 `classroom-sync` Web 进程中运行学生代码。受控执行发生在已经分配给该学生的隔离实验环境中，并满足：

- 固定 C++17 编译器镜像／工具链版本；
- 禁止网络；只挂载本次工作目录和临时目录；
- 编译超时、单测试超时、内存、进程数和输出大小上限；
- 每个测试使用新子进程；超时或异常后强制回收；
- 诊断信息移除宿主绝对路径、凭据和环境变量，只保留有界摘要。

如果运行环境不能提供这些隔离条件，功能必须返回“课堂测试环境不可用”，不得降级为在后端宿主机直接执行。

### 结构化证据事件

新增版本化 `assessment_run` 事件，而不是把普通运行伪装成测试通过。事件至少包含：

- `plan_id`、`plan_version`、`profile_content_hash`；
- `source_sha256`、`toolchain_profile`；
- `compile_status` 与有界 `diagnostic_excerpt`；
- 每个测试的 `test_id`、`status: passed | failed | timeout`；
- `expected_stdout_hash`、`actual_stdout_hash` 和有界 `actual_stdout_preview`；
- 事件时间、会话序号和完整性哈希。

事件随现有证据 outbox 上传，并被转换为 `chunk-N#event-M` 引用。原始教师测试不发送给 AI；AI 只收到测试 ID、结果和必要的有界证据摘要。

提交 payload 同时携带 `submission_source_sha256`。最终判定只使用与该哈希一致的最新有效 `assessment_run`；学生早期曾经通过、随后修改并失败时，不得继续显示已掌握。若无法建立提交源码、编辑事件与测试运行之间的哈希链，状态只能是 `evidence_insufficient` 或 `review_required`。

## 4. 确定性掌握引擎

掌握引擎只消费以下已经校验的数据：

- 当前会话绑定的不可变 profile；
- 截止时间前已成功上传且连续的过程事件；
- profile 哈希、源代码哈希匹配的 `assessment_run`；
- 源框架哈希、提交源码哈希以及至少一次有效代码变更事件；
- 已发布测评维度、测试映射和教师复核。

对每个测评要求形成 `criterion_result`：

- `satisfied`：存在有效支持事件；
- `violated`：存在有效的明确反证，例如关联受控测试失败；
- `missing`：没有足够事件；
- `conflicted`：支持与反证并存或引用不一致。

知识点状态按固定优先级生成：

1. 数据链、版本或哈希冲突 → `review_required`；
2. 任一必需要求为 `violated` → `not_mastered`；
3. 所有必需要求为 `satisfied`，且至少一次关联测试通过 → `mastered`；
4. 至少一项 `satisfied`，其余仅为 `missing` → `partial`；
5. 全部为 `missing`，或没有有效测试运行 → `evidence_insufficient`。

受控测试失败只影响它在发布方案中映射的知识点；编译失败可以同时成为多个知识点的反证，前提是这些知识点明确要求“代码可编译并运行”。否则只显示为课堂级问题并标记待复核，避免扩大推断。

若提交源码与源框架完全相同却通过测试，系统不自动判为已掌握，而是标记 `review_required`，提示教师检查源框架是否已包含答案。源代码已变化但缺少对应编辑／保存证据时标记 `evidence_insufficient`，不能猜测修改过程。

AI 分析输出只能附加：证据摘要、问题解释、教学建议和最多 3 个有效事件引用。它不能修改 `criterion_result` 或最终自动状态。任何无效引用、越界事件、未发布知识点或无证据负面结论都在服务端拒绝。

## 5. 学生简报与课堂列表

### 学生简报 v2

新增向后兼容的简报 v2 投影。每个知识点包含：

- 自动状态与可选教师覆盖状态；
- `satisfied_items[]`、`missing_items[]`、`violated_items[]`；
- 每项对应 `evidence_refs[]`；
- 关联测试汇总；
- 基于当前缺口的一条下一步建议；
- `source: deterministic | teacher_override`。

旧 v1 `not_demonstrated` 在读模型中统一投影为 `evidence_insufficient`，但不改写历史存储。新接口明确支持 `not_mastered`，旧客户端在迁移窗口内继续接收兼容字段。

教师视图可查看测试名称、状态、有界输出摘要和事件引用；学生视图只展示自己的达标项、缺失项、失败测试与下一步操作，不显示教师内部备注、AI 置信信息或其他学生数据。

### 课堂列表

列表主结论完全由后端 `mastery_overview` 生成，前端不计算、不补零、不用示例学生代替真实数据。每名学生一行显示：

- 已掌握、部分掌握、明确未掌握、证据不足、待复核数量；
- 首要问题：优先明确未掌握，其次部分掌握，再次待复核和证据不足；
- 证据覆盖数与最近一次有效受控测试时间；
- “查看简报”入口。

班级顶部汇总同样来自真实学生简报。尚未产生简报的学生显示“等待学生证据”，不进入掌握比例。页面明确提示“缺数据不等于未掌握”。

### AI 建议的幂等性

教师方案 AI 建议按编写会话只生成一次。学生简报的 AI 教学建议按 `source_brief_id + revision` 只生成一次并持久化；刷新页面只读取，不触发再次生成。重新提交形成新简报修订时才允许产生新的分析任务。

## 6. 教师配置页面

向导保持四步：

1. 题目与知识点；
2. 配置测评维度；
3. 时间与采集；
4. 确认发布。

第二步采用已选定的“左侧知识点导航 + 右侧聚焦编辑”：

- 顶部显示服务端恢复的一次 AI 建议状态；成功后只有“使用本次建议”与“继续手动编辑”，没有重新生成；
- 左栏显示每个知识点的“已填写／待完善”状态；
- 右侧只编辑当前知识点的测评维度，显示真实关联测试数量与覆盖状态；
- 源框架与测试用例来自父实验材料，只读展示，不提供尚未接入的上传、下载、导入或 AI 生成按钮；
- 缺测评维度、缺启用测试、测试未覆盖知识点、源框架校验失败时不能进入发布；
- 第四步展示当前哈希确认结果，教师确认后才发布。

页面上的完成度仅表示“配置是否完整”，不能表示学生掌握程度。

## 7. 权限、隐私与审计

- 所有编写会话、建议任务、草稿、发布和复核接口都验证教师对父实验的所有权。
- 学生只能读取自己的分配方案和提交自己的证据；教师只能读取所拥有课堂的学生简报。
- AI 提示将题目、代码摘要和事件视为不可信引用；不执行其中命令。
- 建议任务成功后清除原始题目输入，只持久化安全结果与输入哈希；课堂证据按既有保留策略处理。
- 记录编写会话创建、AI 建议请求／完成、测试与维度确认、发布、受控测试、自动判定和教师覆盖审计事件。
- 列表接口不返回完整源代码；详细证据按需读取并受权限与大小限制。

## 8. 迁移、兼容与发布顺序

数据库使用增量迁移新增编写会话和建议关联字段，不破坏现有任务表。profile v2、Python 规则和 student brief v1 保持可读；C++ 新课堂只使用 profile v3 和 brief v2。

推荐发布顺序：

1. 契约、schema registry 与数据库迁移；
2. `classroom-sync` 编写会话、建议幂等和 v2 简报读模型；
3. 学生插件 C++ 受控测试与 v2 证据事件；
4. 使用真实 C++ 材料完成端到端验证；
5. 教师前端在功能开关下启用四步配置页和新列表；
6. 验证旧 Python 课堂无回归后逐步放量。

回滚时先关闭前端功能开关，再回滚学生插件；服务端保留新增表和可选字段，避免删除已产生的审计与简报数据。旧客户端继续使用 v1/v2 合同。

## 9. 测试策略

### 合同与后端

- profile v2 Python 回归与 profile v3 C++ 正反例；
- 同一编写会话在并发标签页、刷新和重复 POST 下只产生一个建议结果；
- 建议请求后修改题目时返回旧输入标识，前端不得静默覆盖新内容；
- 不同已关闭／新建会话可以各产生一次建议；
- 越权访问、过期会话和发布事务回滚；
- 测试、知识点、维度、源框架哈希确认与失效；
- brief v1 到读模型的兼容映射，以及 brief v2 五种状态。

### C++ 运行器

- 编译成功、编译失败、测试通过、输出不匹配、超时、超量输出；
- 路径穿越、符号链接、任意 flags、网络访问和进程逃逸被拒绝；
- 每次结果携带正确 plan/profile/source/test 哈希；
- 最终提交源码哈希只匹配当前源码的测试结果，历史通过不能覆盖当前失败；
- 诊断摘要不包含宿主路径、环境变量或凭据；
- 普通成功运行不能产生 `mastered`。

### 掌握规则

- 全要求满足且有关联测试通过 → 已掌握；
- 部分要求有证据、其余缺失 → 部分掌握并列出缺项；
- 无上传或证据链不完整 → 证据不足；
- 关联受控测试明确失败 → 明确未掌握并引用该事件；
- 哈希不匹配或证据冲突 → 待教师复核；
- AI 返回负面结论但无有效引用时被拒绝，且不改变确定性状态。

### 前端与端到端

- 编写会话恢复、一次建议应用、成功后无重新生成入口；
- 知识点切换与本地编辑保留、空维度聚焦错误；
- 缺材料或覆盖不完整时发布按钮禁用并显示真实原因；
- 列表使用多名真实测试学生覆盖五种状态，不使用生产占位数据；
- 教师从列表进入简报后能追溯首要问题到测试／事件；
- 学生运行测试、修复代码、再次运行、提交后状态按新证据更新；
- 200% 缩放、键盘导航和窄屏布局。

## 10. 验收门槛

只有同时满足以下条件才可称为“完整可信闭环”：

1. 一次 AI 建议由服务端约束，刷新和并发标签页不能绕过；
2. 两份真实 C++ 源框架和对应测试已通过材料适配与哈希确认；
3. 学生当前提交源码在隔离环境中通过真实教师测试，并产生可追溯的源码—测试—事件哈希链；
4. 五种状态均有确定性测试覆盖，缺数据从不变成未掌握；
5. 课堂列表和简报只展示后端真实读模型，所有问题都有证据引用；
6. 教师覆盖保留原结论与审计；
7. 旧 Python 课堂、旧简报和旧客户端核心流程回归通过。

## 非目标

- 不让 AI 自动发布方案、自动修改教师维度或决定最终掌握状态；
- 不提供任意编译命令、任意脚本执行或在 Web 服务宿主机直接运行学生代码；
- 不在本期实现隐藏测试、抄袭判定、分数／权重、班级排名或学生能力画像；
- 不强制限制学生只能修改源框架中的某个代码区段；首版评价最终源码与真实过程证据；
- 不新增没有 FinColab 材料接口支撑的上传、下载或源文件管理按钮。
